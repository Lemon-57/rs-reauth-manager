# 账号导入

工具栏选择“导入账号”，可一次输入多行，每行一个账号，以下四种格式可混合，支持超过 100 行：

```text
邮箱----密码----2FA
邮箱----密码----2FA----RT
邮箱----密码----邮箱密码----2FA
邮箱----密码----邮箱密码----2FA----RT
```

单批内容最多 500 KiB；待处理导入资料的总内存预算为 2 MiB，任务状态仍受宿主 256 KiB 单条记录容量保护。容量不足时整批不入队，等待现有队列处理后再提交，或适当拆分。没有固定 100 行或 200 行上限，容量以内的全部行一次入队。

不含 RT 时通过受保护管理入口创建 RS 原生 OAuth 流程，插件仅返回授权码回调，RS 交换和保存 RT。未提交工作区选择时，上游返回有效回调即可继续导入；插件不需要预先证明工作区唯一，也不把页面中的候选信息当作已选工作区。最终以 RS 原生保存的账号及两枚令牌共同确认的工作区为准。如果上游要求选择，优先选择唯一明确的 Team/Business，多个团队不自动任选；已选择的工作区必须与保存结果一致。识别为 Free 则保持暂停。原生保存后继续刷新、身份和启停读回流程。

新账号包含 RT 时先通过受保护 RT 导入接口验证并保存。双令牌证明邮箱、用户、主体、工作区、套餐及有效期后，Team/Business 直接启用，不发起账密登录或设备退出。Free 保持同一账号及固定代理，进入普通手动重新授权队列，按现有唯一 Team 成员资格规则处理。不能从 RT 的字符串外观推断套餐。

整批先校验格式并按忽略大小写的邮箱去重；任一行格式无效、邮箱重复（同一批或已排队/执行的导入）或不符合下述存量更新条件时，整批不入队。已有授权正在执行时仍可提交；新导入等前面的授权及导入任务完成后逐行串行处理，不暂停或取消旧任务，也不提前创建授权流程。页面保留仍在队列的各批进度和取消入口。一行失败不重放该行，继续处理下一行。

关闭浏览器后由后台继续；排队资料和原管理员认证仅存于插件当前进程内存。若插件进程重启，未完成行标记中断；若原认证失效，受保护入口仍拒绝。均须核对状态后按需手动处理，不从持久状态重建密码、认证或 RT，不自动重放。旧版单账号接口也使用同一队列，保留原请求标识，提交成功表示已受理而不是登录已开始。

导入前完整分页匹配，邮箱忽略大小写。唯一匹配且确认无在途请求的已有 OpenAI OAuth 账号，无论状态，都接受 `邮箱----密码----2FA----RT` 或 `邮箱----密码----邮箱密码----2FA----RT`。这两种格式由 RS 验证并更新原账号 RT；账密和 2FA 不用于登录，也不覆盖备注。保留账号、固定代理、启停、分组及到期时间，不占新导入的权重序号，验证通过后按下述 Team 调度规则收尾。重复导入未带 RT、身份不明确或无法确认账号空闲时，整批不入队。

重复导入需要宿主 `/api/admin/accounts/oauth/replace-rt` 支持同时启用 `allowPlanMismatch`、`allowWorkspaceAndPlanChange` 和 `allowAnyStatus`。必须匹配原邮箱、用户及 OAuth 主体。同工作区不因套餐不同或未声明而拒绝，也不修改保存的套餐；工作区变化时，必须由双令牌一致证明新工作区和实际套餐，RS 将它们与 RT 一起写回。分组不变，仅双令牌共同确认 `team` 时应用 Team 调度规则。

重复请求标识只读回原回执。RT 被拒绝、结果不确定或传输中断时不自动重放、不回退登录。

存量 RT 更新失败时，任务记录区分 RS 管理接口与上游 OAuth 的 HTTP 状态。只有宿主提供的上游状态和白名单错误码才会记录；旧宿主或没有收到上游响应时不推断。上游正文、RT 和代理认证不会写入任务记录。

新账号未提供邮箱密码时备注为 `邮箱----密码----2FA`，提供时为 `邮箱----密码----邮箱密码----2FA`。未配置 Mailcom 时邮箱密码仅保存；配置 `mailcomKey` 后，仅在原生 OAuth 要求邮箱验证码时用第三段邮箱密码向 Mailcom 取码。RT 不进入备注、任务状态、普通日志或浏览器存储。提交或关闭弹窗后清空输入。任务状态只保存请求标识、账号标识和安全状态；管理员认证只在当前调用及未完成工作进程的内存中存在。

### Mailcom 邮箱验证码

在插件实例敏感字段配置 `mailcomKey` 后，原生 OAuth 遇到 `email_otp_verification` 时，会使用账号四段式备注中的第三段邮箱密码调用 `POST https://mailcom.yeahzi.app/get`。请求只发送邮箱、该邮箱密码和取件参数，使用 `X-Key` 鉴权；不发送 GPT 密码、2FA、账号原 RT、完整备注或代理认证。插件只读取 OpenAI/ChatGPT 发件人的新邮件，提取六位验证码并提交到同一条 RS 原生授权流程。

仅四段式备注（`邮箱----密码----邮箱密码----2FA`）启用此功能；三段式备注没有邮箱密码，不会猜测或改用 GPT 密码。Mailcom 未返回新验证码、鉴权失败或接口错误时，任务按失败/待核对收尾，不自动重放登录。`mailcomKey` 和邮箱密码只在当前协议进程内存中使用，不写入任务状态或普通日志。

### GMX 重新授权 RT 回退

在插件实例敏感字段配置 `mailshopRtApiKey` 后，符合条件的已有 `@gmx.com` 异常账号首次重新授权先走原生 OAuth。若明确要求邮箱验证码、拒绝密码或拒绝已有的 2FA 动态码，同一任务单次调用 `POST https://mailshop.closeai.hk/api/user/gpt/codex-rt/run`，无需再点击。原生登录网络错误、限流和封禁不触发回退。

最近一次已确认的授权结果是上述登录拒绝或 Mailshop 未取得 RT 时，再次手动点击“重新授权”会新建 Mailshop 请求，不启动原生 OAuth。没有可确认的失败依据、已成功授权、写回结果不明、新增导入、指定工作区或未启用 Mailshop 时，不走这条路径；自动任务不会直接使用历史失败重试 Mailshop。

可用 `mailshopRtEmails` 限定允许向 Mailshop 提交的邮箱，比较时忽略大小写。未配置列表时使用常规 GMX 规则；空列表禁止所有 Mailshop 回退，不影响原生重新授权。

启用会向 Mailshop 提交该账号的邮箱、GPT 密码和 2FA 密钥。插件不发送邮箱密码、原 RT、完整备注或固定代理认证，也不能保证 Mailshop 自身的登录出口。返回唯一且邮箱匹配的候选 RT 后，直接交给支持 `allowWorkspaceAndPlanChange` 的 RS 原生 `/api/admin/accounts/oauth/replace-rt`。RS 使用原固定代理交换，验证原邮箱、用户 ID 和 OAuth 主体，并按精确凭据版本将双令牌共同确认的工作区和套餐连同 RT 写回。插件不再另取凭据重复校验令牌，只读回保存标记、凭据版本和账号状态。保留启停，按下述 Team 调度规则收尾；仅 Free 变为非 Free 时按下述规则移动分组。结果不明时不重放。

未取得 RT 时，任务显示「需要核对」及本次结束时间，并显示 Mailshop 的 HTTP 状态、业务错误码以及可安全展示的 `msg` 或本次账号失败原因 `{error}`。响应没有可展示原因，或原因疑似包含凭据、URL、验证码等敏感数据时，只显示错误类别和可用的错误码；不透传原始响应。未取得 RT 不写回，也不自动重试。

### 原生重新授权的套餐与工作区

已有账号普通重新授权时，优先沿用原工作区。如果需要选择且原工作区不可用，可选唯一候选；手动重新授权也可沿用上游会话已明确选中、且在可选列表中的工作区，包括多个 Team 中已明确选中的一个。不随机选取多个候选，现有唯一 Team 升级规则不变。支持 `expectedIdentityRevision` 的 RS 在原生 OAuth 写回前核对邮箱、用户 ID、OAuth 主体及双令牌一致性，允许实际套餐或工作区发生变化。插件按新资料完成刷新读回，再沿既有调度规则恢复。身份或读回不一致时保持暂停；工作区不匹配本身不触发 Mailshop。

原生重新授权或 Mailshop RT 写回证实原 Free 账号变为非 Free 时，即使仍有在途请求，也使用纯分组更新将其移入唯一启用的 `GPT Pro` 分组，并读回确认。移组不取消在途请求、不改启停，也不放宽 RT 写回、刷新及恢复调度的在途检查。分组不存在、重名、停用或账号配置或凭据版本已变化时标记待核对，不重复写 RT。

## Team 调度

实际套餐确认是原始 `team`（页面可能显示 Business）时，新导入、原生手动/自动/批量重新授权、已知 RT 更新及 Mailshop RT 写回统一设置并发 **5**、权重 **1**，不沿用旧套餐的调度值，也不占 Pro/ProLite 的每日序号。只更新这两个设置并读回；身份、代理、日期、分组和启停仍走各自现有规则。按原始套餐判断，不按分组或显示名判断；`business`、按量 Business、Business Premium 和个人套餐沿用各自规则。

## Pro 批次权重

一次提交中核验为实际 `pro` 的新账号共用同一个权重，带 RT 与不带 RT 的行可以混合。每台 RS 按北京时间每日从 50 递减到 1，每个含 Pro 的新批次只占一个序号，并接续当天已有的分配。批次权重在第一个 Pro 获得分配时确定，后续账号即使跨过午夜也沿用它。

Pro 和 ProLite 新导入并发为 20。`prolite` 继续逐账号使用独立的 100 起递减序列，`self_serve_business_prolite` 保持固定权重 20。不改存量或历史分配；实际套餐仍为 Pro 或 ProLite 的普通重新授权保留原并发和权重。

## 受保护管理集成

管理员需设置 `protectedManagementUrl` 为本机回环 HTTP 地址并带端口。导入文本不能控制管理 URL；插件仅向固定的四条路径转发原管理员认证。不配置时拒绝导入，普通重新授权继续使用原逻辑。

适配入口须先校验原管理员会话，使用当前有效管理服务分配预建槽、验证固定认证出口并登记原生 OAuth flow，返回该 flow 的确切代理。原生完成与 RT 导入必须交给同一受保护管理层，以保留永久 IPv6 归属、不复用、消费者保护及账号绑定。不能用临时代理或直接宿主导入替代这项集成。

公开插件不内置站点管理员凭据、真实账号、代理认证或服务器配置。部署适配器属于站点运维材料，不随插件公开发布。
# 付费个人账号与原生流程回执

版本 0.1.60 支持新增 Plus、Pro、ProLite、ProMax 和 Go 账号，仍由 RS 原生 OAuth 完成接口交换并保存 RT。启用前核对邮箱、双令牌主体、工作区、实际套餐、精确凭据版本、备注、分组与固定代理，并完成 RS 原生 RT 刷新及保存读回。Free 账号仍按原暂停及归组规则处理。

管理接口 `api/import-line` 可选传入 `concurrencyLimit` 与 `weight`；省略时新增账号显式使用并发 3、权重 1。导入时先保持暂停，全部核验成功后启用付费账号。

本机适配器新增必需参数 `--state-dir`，目录应仅供管理员访问。原生开始请求的意图和成功回执以私有文件保存；相同请求可读回已有流程，结果不确定时拒绝重建流程。新请求不能覆盖旧请求、释放预留或更换已有出口。迁移适配器前须确认无活动授权，保留旧进程、代理预留和恢复材料，待验证成功后再切换管理入口。

插件和受保护 fleet 管理入口均更新后，如果原生 OAuth 在提交完成前已明确失败、完整目录没有该邮箱且旧预留未绑定账号，管理员可重新提交同一邮箱，无需等待旧 OAuth 链接过期。新流程关联上一条失败的开始请求 ID，单独预留固定出口；旧回执及预留保留，但旧回调不能再提交。未开始登录的中断仍可恢复同一回执；已经提交完成、结果不确定或已存在账号时不会借此重开。

用户提供的 RT 换取失败时明确显示该阶段，不自动改用密码或 2FA 登录。需要重新登录时应由管理员另行明确提交不含 RT 的原生授权任务。



## 中断后的精确恢复（0.1.66）

页面推进请求只返回后台受理状态；耗时操作由宿主 maintenance 生命周期执行，页面刷新、关闭不再携带或取消这些操作。宿主维护本身被取消时仍进入待核对，不自动提交未知结果。

不含 RT 的导入提交时持久化非敏感的原生开始请求 ID。管理员重新提交同一邮箱后，仅最新一条尚未启动登录、没有保存账号的中断记录可复用该 ID。受保护管理层取回同一未消费原生流程及固定出口，插件确认回执有效期足够后才启动登录。不会重新调用原生 start 分配新出口，也不用等待固定的 15 分钟。不同 ID、旧版本无 ID、已进入登录/完成阶段、已入库或包含 RT 的导入不自动恢复。

独立 IPv6 管理入口已有精确 ID 回执能力。固定池实例可使用 `management/exact_start_recovery.py` 加载经摘要核验的当前适配器，为新请求保存原生开始回执，并在完整目录、阶段、邮箱、固定认证、归属、有效期和实际出口检查通过后取回同一结果。适配器保留各实例现有分配策略、映射、原生完成与 RT 导入实现；旧流程没有完整回执时保持待核对。登录输入和 RT 不写入任务状态，原生回执仍只保存在原受保护私有目录。

## 导入账号信息

每个导入任务开始执行时记录开始时间，到期时间为该时间加 30 天，按连续 720 小时计算。同一任务恢复沿用原时间；普通存量重新授权保留原起止时间。

导入成功后账号名称使用完整邮箱。Team、Business 和 `self_serve_business_prolite` 未填写供应商时默认为 `AI_change_future`，已有供应商保留。起止时间、名称与供应商在账号启用前保存并读回核对；不一致时保持暂停。历史账号不因插件升级批量改写。
