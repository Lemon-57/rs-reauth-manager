# 协议适配差异审查

本次审查对应 v0.1.18 的修复。审查和离线对照没有重新登录真实账号、轮换令牌或修改账号状态；发行、安装和实际验收状态以 Release 及部署回读为准。

## 对照基线

- 原项目：`boji1334/reauth-web`，提交 `db8251817fd1baefc83c14c851135fb6078bc001`。
- 五个 `vendor/lib` 协议模块与上述提交逐字节一致；问题和修复均在适配层或公开宿主边界，不修改这些模块。
- 对照原项目 `app/engine.py` 的真实入口，在禁止真实网络的同一模拟传输下运行：授权页正常返回、会话 dump 返回 403、页面 JSON 提供唯一工作区。修复前原项目继续选择并完成模拟令牌交换，插件提前退出；修复后两者均完成上述流程。
- 这证明已修复对应控制流缺陷，不代表已验证某个真实账号当前一定能够登录，也不证明上游拒绝某次会话查询的具体原因。

## 已修复

| 问题 | 本地修复与覆盖 |
| --- | --- |
| Free 检查从会话读取失败处抛错，阻断原库的页面解析后备路径 | 返回到页面解析，覆盖 dump 403、dump 超时和 Cookie 元数据缺失 |
| 暂无工作区 ID 的中间授权页被当成最终失败 | 允许原库继续处理下一步地址，跳转穷尽后才使用该阶段的失败证据，不覆盖后续真实错误 |
| 会话查询的 HTTP 403 被套到“没有 Free 工作区”的本地判断 | 独立 `session_lookup` 阶段；本地候选判定不沿用无关 HTTP 状态 |
| 原工作区 ID 只要出现在页面任意文本或较长 ID 中就被接受 | 从有界 JSON/页面 hydration 数据提取关联字段，精确匹配 ID，不执行 JavaScript |
| `(None, next_url)` 被当作成功绑定，即使选择接口返回 403 | 工作区和组织选择失败立即停止；只有成功接受指定工作区选择才建立绑定依据 |
| `workspaces` 非列表或 null 导致异常 | 防御性处理并保留可用 HTML 后备路径；成功绑定后不进行多余会话解码 |
| 重复或超量候选被缓存重新放回，绕过拒绝规则 | 缓存仅接收已验证候选，合并超限整体拒绝，不截成前 30 个 |
| Cookie 只剩个人工作区时，在检查当前页面之前就自动降级 | 当前页面若包含原工作区，优先保留原工作区 |
| Free 换令牌沿用上游默认自动跟随重定向 | 仅对令牌交换关闭重定向，防止 307/308 转发授权码与 verifier，保留具体拒绝原因 |

页面解析保留候选的类型和套餐证据；多候选、重复、冲突、畸形或过大数据不自动挑选。最终仍要求同一邮箱、用户、选中工作区和有效 Free 令牌；Rust 写回层另核对原主体及精确凭据版本。
引用式 hydration 会解析关联工作区对象而不是只扫描第一个 UUID，保留 Team/个人类型；页面脚本中的 JSON 按原始脚本文本读取，不对工作区名称里的 HTML 实体作二次解码。会话查询的传输失败与本地候选判定分开，不把旧超时放到新的多候选错误上。

## 有意保留的差异

- 原项目自行生成最简 OIDC 授权 URL。插件普通授权保留 RS 拥有的 state、PKCE、回调地址及桌面参数，不能擅自替换 verifier。尚未确认额外桌面参数本身造成具体缺陷。
- 原项目默认取第一个可用工作区。插件不能照搬：原 Team 仍可用则绑定原工作区；只剩个人 Free 时验证恢复并停调度；源记录为 Free 且加入唯一明确团队工作区时自动切换并开启调度。其他多候选变更仍需明确目标，不随机选择。
- 固定使用原账号代理，不因失败随机换代理或改为直连。
- 有界会话恢复和不同动态码重试不无限循环，不自动重放令牌交换或写回，不因登录恢复重置任务总时限。

## 尚需修复的宿主边界

**高优先级：RS 原生普通重新授权的写回前身份比较。**

本地对照的 RS v3.29.2 源码中，`credential/oauth.rs::complete_claimed_authorization` 在普通重新授权分支调用 `prepare_refreshed_oauth_rotation`。该方法按正常 RT 刷新语义替换令牌并保留已有身份资料，没有将新令牌主体与原用户、工作区和主体进行完整比较。插件随后比较账号资料，无法发现被宿主刻意保留的旧资料与新令牌不一致。

因此不能宣称原工作区普通原生授权已具备与 Free 恢复及自动 Team 切换相同的写回前身份保护。旧版自动工作区切换曾使用独立 PKCE 和原主体校验；2026-10-20 用户要求所有授权统一原生协议后，该例外已移除。当前先暂停空闲账号、调用原生完成接口，再核对令牌实际身份；失败保持隔离，不宣称已修复宿主写回前的身份验证缺口。此项须在宿主原生完成路径持久化之前修复，不能在插件中使用别的 verifier 交换 RS 的授权码，也不能把写回后的检测当成事前保护。

本次只记录源码审查发现，没有修改另一工作区中的 RS 源码，没有构建或部署宿主，也没有用真实账号触发此边界。该问题与会话 dump 403 是独立问题。

## 回归入口

### v0.1.20 的组织工作区识别

一次单号结构诊断在工作区选择前停止，未提交选择、交换令牌、写回或启用账号。上游授权页提供一个 `kind: organization` 的组织工作区和一个 `kind: personal` 的个人工作区，会话 dump 未提供可用证据。旧适配器只把 `team/business` 类型视为自动升级候选，因此忽略组织工作区，继续使用原个人 Free 授权并报告普通授权成功。

现在将唯一、不与个人或非团队套餐信息冲突的 `organization` 纳入候选。组织类型本身不证明 Team 套餐：仍通过独立 PKCE 换取所选工作区授权，由 AT 和 ID Token 同时验证邮箱、用户、主体、工作区及实际 Team/Business 套餐，再执行原有 SDK 凭据版本 CAS、读回和启用流程。多个组织候选仍要求手动选择；缺少类型证据的未知候选不自动升级。回归使用虚构工作区标识，覆盖真实观察到的字段结构、会话与页面来源、多组织、个人冲突、非团队令牌及用户变化，不保存真实页面或账号资料。

### v0.1.18 后的解析预算修复

一次明确授权的诊断登录在原账号代理下停止于工作区页面，未提交工作区选择、换取令牌、写回或变更调度；页面原文、Cookie 及登录材料未持久化。安全结构诊断显示：约 73 KB、11 个脚本的授权页触发了赋值扫描第 65 个匹配，且候选遍历计数仍为零。原项目的 HTML 提取器可识别候选，这证明该次拒绝发生在检查实际候选之前，不能把它解释为工作区冲突或账号没有 Free 空间。

本地修复将普通脚本赋值与 JSON 入口分别处理，跳过字符串、注释和比较表达式，仅对可解析的结构化 JSON 入口累计文档预算；页面大小、引用深度、候选数量与冲突检查不取消。新增多于 64 个普通赋值、普通字符串及比较、伪嵌入入口和真实上游库模拟恢复回归。该诊断没有验证修复后真实账号的完整登录，不能把离线通过称为实际 RT 获取成功。本地后续修复未包含在已发布的 v0.1.18 中。

### 两账号真实 Free 写回验收

后续在明确授权的两个账号上，使用仅允许这两个账号的独立验证插件和各自原代理，实测独立 PKCE、身份校验及 SDK 凭据版本 CAS 写回。两个原账号均通过原生管理接口回读：新 RT 与测试前不同，AT/ID 令牌套餐均为 Free，用户、OAuth 主体和最终工作区一致，调度关闭，原备注、分组、代理和其他受保护配置不变。未将令牌、密码、2FA、Cookie 或页面原文保存到验收记录。正式主插件和其任务队列未替换，其他账号配置未变；临时验证实例已停用。该验收覆盖明确指定的 Free 恢复路径，不代表已验证普通原生重新授权的宿主边界。

实测补正两项适配：源记录已经为 Free 时，明确退回 Free 可接受同一原工作区，但仍要求最终真实 Free 令牌及同用户/主体校验；停用后 RS 合法返回 `disabled`，不能因其不是 `normal` 而把已完成写回误报为待核对。首个账号的旧任务提示通过独立凭据回读核实，未重新登录或再次轮换有效 RT。修复后的第二个账号任务直接报告成功。上述修复纳入 v0.1.19，不覆盖既有 v0.1.18 发行包，也不能据此宣称旧版已包含修复。

- `verification/test_workspace_pages.py`：结构化页面数据、转义 hydration、精确 ID、重复/冲突/数量及大小边界。
- `verification/test_fallback.py`：会话读取失败后的页面恢复，以及同一用户、工作区、Free 套餐和 PKCE 防护。
- `verification/test_vendor_contract.py`：被拒绝的选择不能产生普通回调、畸形 Cookie、旧 Cookie 与新页面、无效候选缓存等真实上游库离线场景。
- `verification/test_tracing.py`：会话查询独立阶段和令牌交换禁止跟随重定向。
- 原有 MFA 分类恢复、SDK CAS、在途保护、批次、直接提交和错误显示测试仍需一并通过。

## v0.1.21 自动任务边界

自动巡检不复用上述普通原生完成分支。自动任务在原代理上生成独立 PKCE，以原工作区取得令牌，Python 与 Rust 均核对 AT / ID Token 的用户、邮箱、工作区及套餐，Rust 进一步核对原凭据主体和版本，随后通过公开 SDK 原记录替换并读回。缺失原主体证据时停止，自动任务不切换工作区或套餐。普通手动原生流程的既有宿主边界仍保持上述说明。

## 2026-10-20 统一原生 OAuth

当前所有授权统一使用 RS 原生 start/complete：适配器保留原始 state 与 PKCE，只返回授权码回调；不再运行旧版独立 PKCE/token-exchange 分支。设备退出后也改用 RS 原生账号 refresh。上文描述旧版令牌交换的对照记录仅为历史诊断，不能作为重新引入插件交换 RT 的依据。
